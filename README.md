# pdf-field-extractor

[![tests](https://github.com/xd6ka/pdf-field-extractor/actions/workflows/tests.yml/badge.svg)](https://github.com/xd6ka/pdf-field-extractor/actions/workflows/tests.yml)

Pull structured fields out of invoices with a 3B model on a laptop CPU — and
report field-level precision, recall and F1, hallucination rate, and how often a
value is grounded in the document rather than plausible.

The interesting number is not the F1. It is that **99.5 % of returned values are
literally printed in the document, and one of them is still wrong**. Grounding
and correctness are different properties, and a pipeline that only checks the
first one ships the second kind of error.

Part of a three-project set measured on the same machine: this extractor,
[agent-toolbench](https://github.com/xd6ka/agent-toolbench) (a tool-calling agent
with its own reliability benchmark), and
[rag-service](https://github.com/xd6ka/rag-service) (a RAG pipeline served with
measured p50/p95).

## Numbers

21 synthetic documents, 7 layout variants × 3, `qwen2.5:3b`, CPU, `temperature 0`.

| configuration | docs exact | micro P | micro R | micro F1 | hallucination | grounded | arithmetic caught |
|---|---|---|---|---|---|---|---|
| single pass, no repair | 19/21 (0.905) | 0.995 | 0.989 | 0.992 | 0.167 | 0.995 | 3/3 |
| + validation-driven repair | **20/21 (0.952)** | **0.995** | **1.000** | **0.997** | 0.167 | 0.995 | 3/3 |

Per field with the repair pass: invoice number, date, vendor, currency, subtotal,
tax, total, purchase order — all P/R/F1 = 1.00; payment terms P 0.947, R 1.00,
F1 0.973. Cost: mean 14.4 s per document, median 13.5 s, 1.1 model calls per
document. Arithmetic consistency: 3 of 3 deliberately broken totals detected,
0 false alarms on 18 consistent documents.

Reports are committed: `eval/reports/extract.json` (with repair) and
`eval/reports/extract_norepair.json` (ablation).

## Pipeline

```
PDF ──pypdf──▶ lines ──retrieval──▶ per-field evidence ──qwen2.5:3b──▶ JSON
                     │                                              │
                     └───────────────▶ normalise ──▶ schema ──▶ repair ──▶ values + source line
                                                        │
                                                        └──▶ subtotal + tax == total ?
```

1. **Text layer.** `pypdf` gives one line per printed line. No OCR: a scanned
   invoice is out of scope, and the README says so instead of pretending.
2. **Retrieval.** Each field gets its best lines by keyword score, plus the head
   of the document as fallback. The model never sees a 40-line page when it
   needs one number, and each value keeps the line it came from.
3. **One JSON call per document**, all nine fields, `format=json`.
4. **Normalisation.** Money becomes `1234.56` from `€1.234,56`, `$1,234.56` or
   `0`; dates become ISO from `03.09.2025` or `14/01/2024`; identifier fields
   must match their code pattern or become `null`.
5. **Schema validation.** Required fields, value shapes, and
   `subtotal + tax == total` within 0.02.
6. **Repair pass.** For a field that failed validation, or a field answered
   `null` while the document visibly prints a value of that shape, the model
   re-reads only that field's evidence. At most two repairs per document.
7. **Grounding check.** Does the returned value appear on a line? Reported, not
   enforced — see the footer case below.

## What the corpus is for

Each of the seven variants isolates one failure a document extractor actually
makes, and the gold file stores `present` flags, so "the field is absent" is
itself a scored claim.

| variant | what it stresses |
|---|---|
| `plain` | baseline: `Subtotal: €560.53` on one line |
| `columns` | label column and value column at separate x positions |
| `distractor` | a previous balance, a ship-to party, a second date |
| `aliases` | `Subtotal (excl. VAT)`, `Balance due`, `VAT` |
| `no_po` | purchase order genuinely absent — the answer must be `null` |
| `no_terms` | payment terms genuinely absent, with a footer that mentions "terms" |
| `inconsistent` | `total ≠ subtotal + tax`, to test the arithmetic validator |

The PDFs are generated by `synth/pdfwrite.py`, a 60-line writer this project owns,
so the corpus is reproducible (fixed seed) and each layout change is a deliberate
experiment rather than a side effect of a PDF library.

## The three failures worth reading

**Grounded but wrong.** In `no_terms_15` the model answered payment terms as
`"Payment within the stated terms. Thank you."` — the footer sentence, verbatim
in the document. A grounding check says yes; a schema pattern (`net 30`,
`due on receipt`, `2/10 net 30`) says no. Fixing this required deciding that
`payment_terms` is not free text, and that decision now lives in `SPECS`.

**Invented when absent.** In `no_terms_16` the model produced `Net 30` for a
document with no payment terms at all. Nothing in the text supports it, so
grounding flags it — this is the one hallucination left in 6 absent-field cells
after the schema pattern was added (down from 3 of 6 before it).

**Right line, wrong silence.** In `distractor_07` the purchase order `PO-83148`
was on the page, next to a discount line and a concatenated `Ship to`,
and the model returned `null`. Validation cannot catch a missing value it was
told is optional, which is why the repair trigger asks a different question:
does the document print something of this field's shape? That question alone
recovered both recall misses, and it is the difference between the two rows
of the table above.

## When the page fights back

The table above is the clean case: seven layouts, all of them typeset. A
single 0.997 says nothing about the documents that actually arrive, so there is
a second corpus of 12 documents built from the `columns` layout and then
degraded — two documents per failure mode, gold values untouched:

| degradation | what the page does | exact | F1 |
| --- | --- | --- | --- |
| `spaced` | one space between every character | 0/2 | 0.839 |
| `wrapped` | every amount split before its last two digits, continuation on its own line | 1/2 | 0.971 |
| `stamped` | `PAID` stamp plus `Original total: €9,999.99` and `Balance carried forward: €1,234.00` | 2/2 | 1.000 |
| `tiny` | type scaled to 5.5 pt, eight lines of `Clause N: standard terms apply` in the footer | 2/2 | 1.000 |
| `rotated` | `/Rotate 90`, same content stream | 2/2 | 1.000 |
| `no_text` | grey rectangles where the text was, no text layer at all | 0/2 | 0.000 |

Overall: doc_exact 7/12 = 0.583, micro precision **1.000**, recall 0.778, F1
0.875, grounded 0.830, mean 25 s, 1.42 model calls. Precision did not drop:
every value it returned for a degraded page was one the page actually printed.
What disappears is recall, and it disappears in ways that are worth naming.

**Two degradations are free.** `rotated` and `plain` produce the identical
`pdf_lines()` output — rotation is a page attribute, and `pypdf` reads the
content stream — so a rotated scan is not a threat model for this pipeline,
whatever it is for a raster-based one. `stamped` is free for a different
reason: the stamp is a second total, the arithmetic constraint
(`subtotal + tax == total`) picks the consistent triple, and the model never
even quotes €9,999.99. Both are in the corpus to prove the guardrails work,
not because they are hard.

**Character spacing breaks labels, not amounts.** In `spaced`, `Subtotal` is
printed as `S u b t o t a l`, the vendor comes back as
`S i e r r a C o m p o n e n t s L t d`, and `2/10 net 30` becomes
`2 / 10 net 30`, which the schema pattern rejects. The money survives because
`normalize_money` strips whitespace before matching. The F1 of 0.839 with
0/2 exact is that split: three fields per document readable, six not.

**A wrapped amount is read twice, wrongly.** In `wrapped-03` the subtotal is
printed as `$4,062.` with `56` below it; the model returns `4062.00`, dropping
the continuation and padding a `.00`, while the total `4346.94` comes back
correct. `4062.00 + 284.38 != 4346.94` fires the arithmetic check with
`delta = -0.56`. Against the gold triple that is a false alarm — the document
is self-consistent — and against the extracted triple it is precisely the right
thing to say: the number is wrong. This is the one case in 12 where the check
caught an error the model made, and it caught it because two independent
readings disagreed.

**The best answer gets withheld.** `wrapped-02` returns all nine fields
correctly, and grounding flags `subtotal` and `total`, because no contiguous
token `415.61` exists on the page — it is `415.` and `61`. The guardrail
cannot see a value the layout broke in half, so the caller is told those two
fields are unsupported. For a downstream system that refuses ungrounded values
this is a false negative on a *correct* extraction; the honest reading is that
the page, not the model, is the source of the doubt.

**No text layer means no guess.** Both `no_text` documents return eighteen
`null`s, three repair calls each, all of them `missing`. The pipeline does not
substitute an empty string for a page it cannot read; a rasterised invoice
needs OCR in front of this stage, and nothing here pretends otherwise.

## Limits

- 21 documents with 9 fields is 189 field decisions, and one document is 4.8
  points of `doc_exact_rate`. The gap between 0.905 and 0.952 is two documents;
  treat it as a direction, not a result.
- Synthetic layouts. Real invoices carry logos, stamps, skewed scans and
  multi-page tables; none of that is here, and none of the numbers above
  transfer to it. The degraded corpus is synthetic too: six named failure modes
  applied in isolation, not a photograph of a fax of a scan.
- One model, one machine: `qwen2.5:3b`, CPU, 4k context, no GPU run.
- No OCR, no tables spanning pages, no multi-currency documents.
- Nothing reaches the network except `localhost:11434`.

## Run it

```bash
python -m venv venv
venv\Scripts\activate            # source venv/bin/activate elsewhere
pip install -r requirements.txt
pytest -q                        # 48 tests: writer, corpus, normalisation, schema, retrieval, grounding, degradation

ollama serve                     # another terminal
ollama pull qwen2.5:3b

python -c "from pathlib import Path; from synth.corpus import build_corpus; build_corpus(Path('data/corpus'), per_variant=3)"
python eval\run_eval.py --out eval\reports\extract.json
python eval\run_eval.py --repairs 0 --out eval\reports\extract_norepair.json

python -c "from pathlib import Path; from synth.degrade import build_degraded_corpus; build_degraded_corpus(Path('data/corpus_degraded'))"
python eval\run_eval.py --corpus data\corpus_degraded --out eval\reports\extract_degraded.json
```

Flags: `--model`, `--repairs N`, `--limit N`, `--corpus path`, `--out path`.
Env: `PDF_MODEL`, `PDF_MAX_REPAIRS`.
